# ADR-006: AI Automation Proxy and Generic Data Store Framework

## Status

Accepted. **Implemented** as commit `4dee56c` (PR #98) in ssetunnel and `35a0e28` in
gemini-automation-extension. The framework's server-side attachment was completed and
`ai-automation-proxy` started persisting job history once the proxy shipped; see
"Job persistence" below. (This document previously cited `17e6a00`, the pre-merge hash of the
same work — that object is unreachable after the merge.)

## Context

AI agents and external clients need to invoke browser-based automation (Gemini,
DeepSeek) that runs inside a WXT browser extension. The extension lives in a
restricted browser context and cannot accept inbound connections or WebSocket
upgrades from external networks. Clients behind HTTP-only proxies also cannot
establish persistent connections to a backend.

Additionally, modules running behind the agent's IPC boundary need a way to
persist structured data (job history, configuration, user preferences) without
direct database access. Each module would otherwise require its own storage
mechanism or direct PostgreSQL connection, violating the principle that modules
communicate only through the control tunnel.

## Decision

Implement a standalone ssetunnel agent module (`ai-automation-proxy`) that
bridges external clients to the WXT extension via HTTP long polling, plus a
generic data store framework that lets any module persist data through the
control tunnel.

### AI Automation Proxy

The proxy runs as a separate process connected to the agent via IPC. It exposes
two HTTP surfaces:

| Surface | Address | Purpose |
|---------|---------|---------|
| Client API | via SDK invocation | `POST /jobs`, `GET /jobs/{id}` |
| Extension Server | local `:9090` (default) | `GET /poll`, `POST /result` |

**Job lifecycle:**
```
Client POST /jobs
    │
    ▼
JobManager.Submit() → pending queue (chan *Job, capacity 256)
    │                    │
    │                    ▼
    │              Extension GET /poll blocks here
    │                    │
    │                    ▼
    │              Extension receives job, marks RUNNING
    │                    │
    │                    ▼
    │              Extension runs automation in browser tab
    │                    │
    │                    ▼
    │              Extension POST /result with response
    │                    │
    ▼                    ▼
JobManager.Complete() → terminal state (completed/failed/timeout)
    │
    ▼
Client GET /jobs/{id}?wait=true → returns final result
```

**Key design points:**
- Async job submission: clients receive a job ID and poll for results
- Pending queue capacity 256; full queue returns `QUEUE_FULL` error
- Per-job timeout goroutine (default 5 min, configurable per-job via `timeout_ms`)
- Extension long-polling with configurable timeout (default 30s, max 5 min)
- 32-character hex job IDs from `crypto/rand`

### Generic Data Store Framework

A new control tunnel message type (`data_store_req`/`data_store_resp`) enables
modules to perform CRUD operations on a server-side PostgreSQL table
(`module_records`).

**Data flow:**
```
Module (sdk.DataStore)
    │ IPC: DATASTORE <len>\n<json>
    ▼
Agent (dataStoreForwarder)
    │ Control stream: MsgDataStoreReq
    ▼
Server (DataStore.HandleRequest)
    │ PostgreSQL: module_records table
    ▼
Server → Agent → Module (MsgDataStoreResp)
```

**Schema:**
```sql
CREATE TABLE module_records (
    id         bigint GENERATED BY DEFAULT AS IDENTITY,
    module_id  text NOT NULL,
    record_id  text NOT NULL,
    data       jsonb NOT NULL DEFAULT '{}',
    created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE (module_id, record_id)
);
```

**SDK API:**
```go
ds, _ := sdk.NewDataStore()
defer ds.Close()

ds.Create(ctx, "com.example.module", "record-1", jsonData)
record, _ := ds.Get(ctx, "com.example.module", "record-1")
records, _ := ds.List(ctx, "com.example.module", &sdk.ListOptions{Limit: 100})
ds.Delete(ctx, "com.example.module", "record-1")
```

**Key design points:**
- Modules open a dedicated IPC connection for data store operations
- Request/response correlation via `request_id` with 30s default timeout
- Server caps `List` at 1000 records; default limit 100
- `Create` uses upsert semantics (`ON CONFLICT DO UPDATE`)
- No module isolation at the database level — modules can read/write any `module_id`

### Job persistence

`ai-automation-proxy` persists its job history through the SDK client, keyed by job id under
its own `module_id`. Semantics:

- **Terminal states only.** `completed`, `failed`, and `timeout` are written once; `pending`
  and `running` stay in memory. In-flight jobs are not resumable after a restart, so writing
  intermediate states would only create rows that no reader can act on.
- **Attachment bytes live in the object store.** A submit requires `byte_length`, checks the
  4 MiB limit, gzips the bytes when that shrinks them, and writes them to the module object
  store (ADR-008). The job keeps `object_key`, `sha256`, and `encoding` plus the file
  metadata, never the bytes. The extension poll reads the object back and restores
  `data_base64`, so the extension contract does not change. A poll makes up to three read
  attempts on transport errors inside a 5-second delivery budget; a missing object or a
  digest mismatch fails at once. A submit that carries a file fails when object storage is
  unavailable; the module has no memory-only path for attachment bytes.
- **MIME filtering is extension-only.** The module checks file shape and size, not the
  extension's allowlist. A submit can succeed for a type the extension rejects at dispatch,
  and that object then stays in the store, which has no delete.
- **Read-through on miss.** `GET /jobs/{id}` checks memory first (in-flight work plus the
  10-minute retention window), then reads the row back. A stored non-terminal status can
  only come from a process that stopped mid-job, so it is reported as `failed` with code
  `ABANDONED` instead of pretending the job still runs.
- **Best effort.** A failed write is logged with the job id and never changes the job outcome;
  the module continues memory-only. When the data store cannot be reached at startup (older
  agent, missing IPC environment), the module logs once and runs with nil store.
- **Rows are permanent.** No TTL exists in `module_records`; retention cleanup is an
  operational decision, not module behavior.

Server-side attachment lives in `internal/command/command.go` (`srv.SetDataStore`): sessions
capture the handler when they attach, so the call must happen before serving starts.

### WXT Extension Integration

Added a long-polling client (`utils/long-poll-client.ts`) that:
1. Reads proxy URL and enabled flag from `browser.storage.local`
2. Polls `GET /poll?timeout=30s` in a loop with exponential backoff
3. Dispatches received jobs through the existing `dispatchAutomation()` pipeline
4. POSTs results back to `POST /result`
5. Restarts on connection failure with exponential backoff (1s → 30s cap)

The existing popup-based messaging flow (`chrome.runtime.onMessage`) remains
unchanged. Long-polling is additive and only active when explicitly enabled.

## Consequences

- External clients can trigger browser automation through the ssetunnel tunnel
  without exposing the extension to inbound connections
- Modules gain persistent storage without direct database access, reducing
  deployment complexity and improving security posture
- The `module_records` table is generic and reusable for any future module;
  `ai-automation-proxy` uses it to keep terminal job history across the 10-minute memory
  window and process restarts
- Extension long-polling is compatible with Manifest V3 service workers (no
  persistent WebSocket required)
- No module isolation in the data store — any module can read/write any other
  module's records by choosing the same `module_id`. This is acceptable for
  the current trust model (all modules run in the same process as the agent)
  but would need tenant isolation for untrusted modules

## Rejected Alternatives

### For the Proxy

- **WebSocket server for extension:** Rejected — Manifest V3 service workers
  cannot maintain persistent WebSocket connections reliably; long-polling is
  the established pattern for background scripts.
- **gRPC streaming:** Rejected — browser extensions cannot use gRPC; HTTP
  long-polling is the only viable transport.
- **Synchronous invocation (block until result):** Rejected — LLM automation
  can take 30–120 seconds; clients should not block that long. Async job
  submission with polling provides better UX and timeout flexibility.
- **Embed proxy in agent process:** Rejected — separation of concerns; the
  proxy can be updated independently and has different lifecycle requirements
  (HTTP listener vs yamux stream).

### For the Data Store

- **Per-module SQLite files:** Rejected — data would live on the agent's host,
  not the server; no centralized backup or query capability.
- **Redis or external KV store:** Rejected — adds operational complexity;
  PostgreSQL already handles JSONB efficiently.
- **Module-specific tables:** Rejected — each new module would require a new
  migration; the generic `module_records` table with JSONB data column
  supports any schema without schema changes.
- **Shared PostgreSQL connection in modules:** Rejected — violates the
  principle that modules communicate only through the agent's IPC boundary;
  would require credential distribution to each module process.
- **REST API directly on server:** Rejected — modules behind restricted
  networks cannot reach the server's HTTP API; the control tunnel is the
  established communication path.

## Security Considerations

- The extension server listens on a local port (default `:9090`) with no
  authentication. On shared hosts, any local process can submit jobs and
  read results. Mitigation: bind to `127.0.0.1` only; use a firewall rule
  or move to Unix socket when needed.
- The data store has no module isolation. Any module can read/write records
  under any `module_id`. Mitigation: acceptable for trusted modules; add
  `module_id` validation or row-level security if untrusted modules are
  introduced.
- Job payloads and attachment bytes travel through the control tunnel. Attachment bytes are
  gzip-compressed before the object-store transfer but not encrypted, and stored objects are
  plaintext files under the operator-owned `0700` root. The tunnel itself is encrypted
  (HTTPS to server, yamux over HTTP), so this is not a concern unless the agent's host is
  compromised.
